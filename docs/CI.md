# CI: что запускается, как включить, как читать результат

## Что запускается

| Workflow | Когда | Что делает |
|---|---|---|
| `core-tests-linux.yml` — «Core tests (Linux)» | каждый push и pull request | пять задач на Linux, 5–15 минут |
| `release.yml` — «Build & Publish Clean Release» | push в `main` и `arena/**` | сборка клиента, лаунчера и сервера под Windows, тесты, установщик; около 20 минут, первая сборка в репозитории дольше |

Задачи Linux:

| Задача | Команда | Что проверяет |
|---|---|---|
| `static-checks` | `Tools/rfab/run-static-checks.sh` | проверки исходников: дисциплина хуков, время жизни актёров (нет указателей движка в отложенной работе, в полях сервисов и событий), контракт провода, инварианты релиза (версия, ревизии сабмодулей), аудит порта под SE 1.5.97; самопроверки инструментов; разбор всех скриптов PowerShell настоящим парсером и самопроверка сборщика отчёта |
| `core-tests` | `Tools/rfab/run-core-tests.sh` | ядро и протокол |
| `core-tests-sanitized` | `Tools/rfab/run-core-tests.sh --asan` | то же под ASan и UBSan, с увеличенным фаззингом |
| `ui-build` | `pnpm run deploy:production` в `Code/skyrim_ui` | интерфейс собирается из исходников |
| `server-harness` | `Tools/rfab/linux-server/run-server-tests.sh` | настоящий сервер на Linux, сценарии через диспетчер пакетов. В CI собирается и выполняется под ASan и UBSan (скрипт сам включает их, когда видит `GITHUB_ACTIONS`); локально — без них, с ключом `--asan` так же, как в CI |

Сборка Windows целиком живёт в `Tools/rfab/Build-CloudRelease.ps1` (восемь шагов: сабмодули и патчи, аудит порта, конфигурация, сборка, тесты, интерфейс, упаковка, публикация).

Те же команды запускаются локально на Linux, кроме сборки Windows.

## Как включить

Workflow-файлы лежат в `.github/workflows-ready/`, а GitHub исполняет только `.github/workflows/`. Приложение GitHub, через которое идёт разработка, не имеет права `workflows` и не может создавать или менять файлы в `.github/workflows/`. Перенос делает владелец репозитория, один раз:

1. Открыть на сайте GitHub файл `.github/workflows-ready/core-tests-linux.yml` **в ветке разработки**.
2. Нажать карандаш («Edit this file»).
3. В поле имени файла поставить курсор в самое начало и набрать `../workflows/`. `../` поднимает файл на папку выше, `workflows/` кладёт его в новую папку; путь над редактором должен стать `.github/workflows/core-tests-linux.yml`. Содержимое файла не менять.
4. Нажать «Commit changes…», оставить «Commit directly to the … branch», подтвердить.
5. Повторить для `release.yml`.

После второго коммита оба workflow запускаются сами (вкладка Actions). Если ничего не запустилось: Settings → Actions → General → «Allow all actions and reusable workflows».

Менять эти файлы после переноса тоже может только владелец. Поэтому в них нет логики: каждая задача вызывает скрипт из `Tools/rfab/`, и всё, что может потребовать изменений, меняется в скриптах.

## Как читать результат

Логи и архивы прогонов из среды разработки недоступны, доступны статусы шагов и аннотации. Поэтому упавший шаг сам сообщает, что сломалось:

| Аннотация | Содержание |
|---|---|
| `DIAG_SUMMARY` | шаг, код выхода, сколько ошибок каких видов и в каких файлах |
| `DIAG_ERRORS_n_OF_m` | первые ошибки по порядку, без повторов: ошибки компилятора и линковщика, упавшие проверки тестов с раскрытием выражения, отчёты санитайзеров, трассировки Python, упавшие проверки исходников |
| `DIAG_LOG_TAIL` | последние 40 строк лога |
| `RFAB_CI` (notice) | успешный шаг Linux: строка результата, например число тестов |
| `RFAB_BUILD`, `BUILD_VERIFIED` (notice) | пройденные шаги сборки Windows |

Linux-задачи получают это через обёртку `Tools/rfab/ci_run.sh`, сборка Windows — через `Invoke-LoggedCmd` в `Build-CloudRelease.ps1`; разбор лога в обоих случаях делает `Tools/rfab/ci_diagnostics.py`.

Прочитать результат прогонов коммита одной командой:

```
./Tools/rfab/ci_status.sh                # прогоны для HEAD текущей ветки
./Tools/rfab/ci_status.sh <sha|ветка>    # для другого коммита
./Tools/rfab/ci_status.sh --wait [ref]   # ждать, пока все прогоны коммита закончатся
```

Скрипт печатает по каждому прогону задачи, текущий шаг незавершённых и все аннотации завершённых. То же вручную:

```
gh run list -b <ветка> -L 4 --json databaseId,workflowName,conclusion,headSha
gh api repos/<владелец>/<репозиторий>/actions/runs/<id>/jobs --jq '.jobs[] | "\(.id) \(.name) \(.conclusion)"'
gh api repos/<владелец>/<репозиторий>/check-runs/<id задачи>/annotations --jq '.[] | "[\(.annotation_level)] \(.title): \(.message)"'
```

### Чтобы один прогон показывал как можно больше

Круг «исправил → запушил → дождался сборки Windows» занимает около часа, поэтому важно, сколько ошибок приносит один прогон.

- **Шаг `[4/8]` собирает три цели по отдельности** — `TPTests`, `SkyrimTogetherServer`, `SkyrimTogetherClient` — и падение одной не останавливает следующую. `xmake` прекращает сборку на первой упавшей цели, и раньше прогон показывал ошибки только её. После трёх целей идёт обычная полная сборка, она и решает, зелёный ли шаг.
- **Аннотации делятся между командами шага.** GitHub показывает не больше десяти аннотаций каждого уровня на шаг задачи, а вся сборка Windows — один шаг. Поэтому `ci_diagnostics.py` принимает `--max-chunks`: тестам и серверу по два блока ошибок, клиенту четыре.
- **Наборы тестов на Linux компилируются без префиксного заголовка**, как в цели `TPTests` под Windows. Раньше `Tools/rfab/linux-core/Makefile` подставлял им `EncodingPch.h`, и набор, которому не хватало `#include`, собирался на Linux и падал под MSVC. Именно так упала первая сборка Windows (38 ошибок из одного пропущенного `#include` в `common/RfabCoopProgression.h`); теперь эта ошибка воспроизводится локально.

- **Скрипты PowerShell проверяются за две минуты, а не за полчаса.** Сборка, упаковка, установщик и сборщик отчёта исполняются под Windows PowerShell 5.1, и ошибка в них раньше была видна только в конце сборки Windows. Теперь задача `static-checks` (на Linux-раннерах GitHub есть PowerShell 7) разбирает каждый `Tools/rfab/*.ps1` настоящим парсером (`Test-PowerShellSyntax.ps1`: синтаксис, операторы, которых нет в 5.1, отсутствие BOM при не-ASCII тексте) и запускает самопроверку сборщика отчёта. Локально, где PowerShell нет, проверка пропускается с сообщением.
- **Успешный шаг сообщает о себе.** Любой скрипт может напечатать строку, начинающуюся с `[RFAB_RESULT] `, — она попадёт в аннотацию-уведомление своего шага (итог тестов Windows, число функций в таблице символов, результат прогона сборщика отчёта на тестовой установке). Из успешного прогона снаружи GitHub видны только уведомления, поэтому всё, что нужно знать о сборке, идёт через них. Уведомлений на шаг не больше десяти: три отдельные сборки целей шага `[4/8]` при успехе молчат.

## Где взять сборку

Каждый прогон `release.yml` прикладывает к себе архив `RFAB_Online-build-<sha>`: установщик, быстрое обновление, символы (PDB и карты линковщика `SkyrimSE.map`, `STServer.map`), контрольные суммы. Архив хранится 90 дней. Скачать: вкладка Actions → нужный прогон → раздел Artifacts.

## Публикация релиза

В этом репозитории CI собирает и проверяет, но релиз на GitHub не публикует: защищённые теги и манифесты резервных копий в `Build-CloudRelease.ps1` описывают историю релизов апстрима. Чтобы разрешить публикацию отсюда, в корень репозитория кладётся пустой файл `RELEASE_FROM_THIS_REPOSITORY`; до этого нужно решить, что делать с проверками резервных копий старых версий (этап 8 плана работ).
